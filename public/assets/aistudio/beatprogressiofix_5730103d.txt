## 1. Kinematic progression prompting

Replace “write a prompt for this narration fragment” with a two-stage generation contract:

1. **Scene plan:** define the causal action chain and the state machine for each important entity.
2. **Beat render:** select the next legal state transition and render only that transition.

Add this to the master system prompt:

```text
You are a storyboard director generating a sequence of distinct visual beats.

A VISUAL BEAT IS NOT A NARRATION FRAGMENT.
A VISUAL BEAT IS ONE PHYSICAL MOMENT IN A CONTINUOUS ACTION.

For every beat, you must advance the scene by changing at least one of:
1. PHYSICAL STATE: door closed -> hand on knob -> door cracked open -> door wide.
2. POSSESSION OR CONTACT: phone in mother's hands -> phone extended -> phone in student's hand.
3. SCREEN OR OBJECT STATE: screen off -> incoming call -> caller ID visible -> static.
4. CHARACTER ACTION: reaching -> gripping -> lifting -> reacting.
5. CAMERA PERSPECTIVE: wide establishing -> over-the-shoulder -> POV -> insert/macro -> reaction.
6. NARRATIVE REVELATION: a new visible fact enters the frame.

STRICT RULES:
- Never repeat the same physical action in consecutive beats.
- Never repeat the same primary subject and same camera framing in consecutive beats.
- Never describe a static scene as a new beat unless it reveals new visible information.
- If the narration fragment does not introduce a new visual event, merge it into the previous beat.
- Each beat must begin with a TRANSITION verb or state change, such as:
  reaches, turns, opens, reveals, extends, takes, grips, lights up, displays, trembles, shifts.
- Do not use generic variation prefixes such as "The altered environment",
  "Emphasizing grounded scale", or "Focusing on tactile textures" to disguise repetition.
- Maintain a scene-local continuity ledger for every recurring character and prop.
- The final image prompt must describe only the exact state reached in that beat.
```

## 2. Physical state-tracking schema

Use a **scene-scoped continuity ledger** plus a **per-beat transition record**. The ledger is the source of truth; the prompt is generated from the ledger, not freely invented.

```ts
type EntityId = string;

type StateValue = string;

interface EntityState {
  entityId: EntityId;
  entityType: "character" | "prop" | "environment" | "screen";
  state: Record<string, StateValue>;
}

interface StateTransition {
  entityId: EntityId;
  field: string;
  from: StateValue;
  to: StateValue;
  trigger: string;
}

interface VisualBeat {
  beatId: number;
  sceneId: string;
  narrationSpan: string;
  startMs: number;
  endMs: number;

  subject: EntityId;
  action: string;
  camera: {
    shotSize: "ECU" | "CU" | "MCU" | "MS" | "WS" | "EWS";
    angle: "eye" | "high" | "low" | "OTS" | "POV" | "macro";
    movement: "static" | "push-in" | "pull-out" | "pan" | "tilt" | "handheld";
  };

  stateBefore: EntityState[];
  stateAfter: EntityState[];
  transitions: StateTransition[];

  visualDelta: string;
  narrativeReveal?: string;

  imagePrompt: string;
  videoPrompt?: string;
}

interface ScenePlan {
  sceneId: string;
  goal: string;
  entities: EntityState[];
  requiredBeats: VisualBeat[];
}
```

## 3. Beat aggregation versus micro-splitting

Do **not** create one image beat per token, word, or sub-clause. Create beats from **visual event boundaries**.

Use this decision procedure for each narration span:

| Condition | Decision |
|---|---|
| Fragment continues the same action, subject, and state | Merge into current beat |
| New verb introduces a physical action | New beat |
| Object changes holder, location, orientation, or condition | New beat |
| Screen/content reveals new information | New beat |
| Camera must change to communicate a new spatial relationship | New beat |
| Fragment is under ~0.6–0.8s and has no state change | Merge |
| Combined beat would exceed ~2.2–2.5s | Split at the next natural action boundary |
| Fragment is a connective such as “pero,” “na,” “sa,” “niya,” “nang” | Never create its own beat |

For your Scene III narration:

```text
Pagbukas ko, putla ang mama ko.
Pinakita niya sa akin ang phone niya na ring nang ring.
```

A good six-beat plan is:

1. **Door opens:** student’s hand turns knob; door cracks open.  
2. **POV reveal:** through the opening, pale mother stands in the dark hallway.  
3. **Offer:** mother extends the Nokia toward the student; screen still dark.  
4. **Transfer:** student’s hand takes and grips the phone.  
5. **Call activates:** screen lights amber; incoming call from unknown number.

### Layer A: exact/near-duplicate prompt

Normalize whitespace, punctuation, casing, and known filler prefixes; compute cosine similarity on embeddings or token Jaccard.

### Layer B: structural event signature

Compare the structured fields, not prose:

```ts
const signature = [
  beat.subject,
  beat.action,
  beat.camera.shotSize,
```

### Layer C: transition validation

A beat is valid only if:

```ts
beat.transitions.length > 0 ||
```

### Repair policy

| Detection | Action |
|---|---|
| `DUPLICATE` and combined duration ≤ 2.5s | Merge narration spans and prompts |
| `DUPLICATE` and combined duration > 2.5s | Re-plan into distinct action beats |
| `LIKELY_DUPLICATE` | Ask the LLM to rewrite Beat N using the state ledger and a mandatory visual delta |
| Valid state change but identical prose | Regenerate prompt from structured transition |
| No legal next state | Change camera perspective or introduce a reaction/insert shot, but only if it adds information |

Never “fix” duplication by prefixing camera language. Either **merge** or **change the underlying event**.

### Stage 2: State-machine validator

Validate each planned beat against the previous beat.

```ts
function validateBeat(prev: VisualBeat | null, next: VisualBeat): ValidationIssue[] {
  const issues: ValidationIssue[] = [];

  if (prev && next.subject === prev.subject && next.action === prev.action) {
    issues.push({
      code: "DUPLICATE_ACTION",
      message: "Consecutive beats repeat the same subject and action."
    });
  }

  if (prev && next.transitions.length === 0) {
    const cameraChanged =
      next.camera.angle !== prev.camera.angle ||
      next.camera.shotSize !== prev.camera.shotSize;

    if (!cameraChanged && !next.narrativeReveal) {
      issues.push({
        code: "NO_VISUAL_PROGRESS",
        message: "Beat has no state change, camera change, or narrative reveal."
      });
    }
  }

  for (const transition of next.transitions) {
    const prior = prev?.stateAfter.find(
      s => s.entityId === transition.entityId
    );

    if (prior && prior.state[transition.field] !== transition.from) {
      issues.push({
        code: "INVALID_STATE_TRANSITION",
        message: `Expected ${transition.entityId}.${transition.field} to be "${transition.from}", but previous state was "${prior.state[transition.field]}".`
      });
    }
  }

  return issues;
}
```

### Stage 3: Deduplication and repair

```ts
type RepairAction = "KEEP" | "MERGE_WITH_PREVIOUS" | "REGENERATE" | "REPLAN_SCENE";

async function repairBeat(
  previous: VisualBeat | null,
  current: VisualBeat,
  scene: ScenePlan
): Promise<RepairAction> {
  if (!previous) return "KEEP";

  const issues = validateBeat(previous, current);

  if (issues.some(i => i.code === "DUPLICATE_ACTION")) {
    const combinedDuration = current.endMs - previous.startMs;

    if (combinedDuration <= 2500) {
      return "MERGE_WITH_PREVIOUS";
    }

    return "REPLAN_SCENE";
  }

  if (
    issues.some(
      i =>
        i.code === "NO_VISUAL_PROGRESS" ||
        i.code === "INVALID_STATE_TRANSITION"
    )
  ) {
    return "REGENERATE";
  }

  const promptSimilarity = await comparePromptSimilarity(
    previous.imagePrompt,
    current.imagePrompt
  );

  if (promptSimilarity > 0.90) {
    const combinedDuration = current.endMs - previous.startMs;
    return combinedDuration <= 2500 ? "MERGE_WITH_PREVIOUS" : "REGENERATE";
  }

  return "KEEP";
}
```

## 7. TypeScript pipeline sketch

```ts
interface BeatCandidate {
  narrationSpans: NarrationSegment[];
  subject: EntityId;
  action: string;
  camera: VisualBeat["camera"];
  transitions: StateTransition[];
  narrativeReveal?: string;
}

export async function buildSequentialBeats(
  scene: ScenePlan,
  candidates: BeatCandidate[],
  renderPrompt: (beat: VisualBeat) => Promise<string>
): Promise<VisualBeat[]> {
  const output: VisualBeat[] = [];
  let previous: VisualBeat | null = null;
  let beatId = 1;

  for (const candidate of candidates) {
    const startMs = candidate.narrationSpans[0].startMs;
    const endMs = candidate.narrationSpans.at(-1)!.endMs;

    let beat: VisualBeat = {
      beatId: beatId++,
      sceneId: scene.sceneId,
      narrationSpan: candidate.narrationSpans.map(s => s.text).join(" "),
      startMs,
      endMs,
      subject: candidate.subject,
      action: candidate.action,
      camera: candidate.camera,
      stateBefore: previous?.stateAfter ?? scene.entities,
      stateAfter: applyTransitions(
        previous?.stateAfter ?? scene.entities,
        candidate.transitions
      ),
      transitions: candidate.transitions,
      visualDelta: describeDelta(candidate),
      narrativeReveal: candidate.narrativeReveal,
      imagePrompt: ""
    };

    const decision = await repairBeat(previous, beat, scene);

    if (decision === "MERGE_WITH_PREVIOUS" && previous) {
      previous.narrationSpan += " " + beat.narrationSpan;
      previous.endMs = beat.endMs;
      continue;
    }

    if (decision === "REGENERATE" || decision === "REPLAN_SCENE") {
      beat = await regenerateBeatWithProgression({
        scene,
        previous,
        candidate,
        beatId: beatId - 1
      });
    }

    beat.imagePrompt = await renderPrompt(beat);
    output.push(beat);
    previous = beat;
  }

  return output;
}

function applyTransitions(
  states: EntityState[],
  transitions: StateTransition[]
): EntityState[] {
  const next = structuredClone(states);

  for (const transition of transitions) {
    const entity = next.find(e => e.entityId === transition.entityId);

    if (!entity) {
      throw new Error(`Unknown entity: ${transition.entityId}`);
    }

    if (entity.state[transition.field] !== transition.from) {
      throw new Error(
        `Invalid transition for ${transition.entityId}.${transition.field}: ` +
        `expected "${transition.from}", found "${entity.state[transition.field]}"`
      );
    }

    entity.state[transition.field] = transition.to;
  }

  return next;
}

function describeDelta(candidate: BeatCandidate): string {
  if (candidate.transitions.length === 0) {
    return candidate.narrativeReveal ?? "";
  }

  return candidate.transitions
    .map(t => `${t.entityId}.${t.field}: ${t.from} -> ${t.to}`)
    .join("; ");
}
```

The most important change is to separate the responsibilities of the planner and the prompt writer.

### Recommended master system prompt

Use the following as a new system-level instruction for your visual beat planning stage.

# StoryFrame — Sequential Kinematic Beat Planner

## Role

You are a cinematic action planner for a short-form AI storyboard generator.

Your task is to transform a narrative script into a chronological sequence of visually distinct, physically plausible moments.

You are not generating a collection of independent illustrations. You are planning a continuous sequence of events that can be filmed as a series of images or video shots.

## Primary objective

Every generated beat must advance the visual storytelling.

A beat must contain at least one of the following:

1. A new physical action or meaningful action phase.
2. A change in an object's or character's physical state.
3. A new, narratively necessary visual revelation.
4. A distinct character reaction caused by the preceding event.
5. A deliberately sustained shot that communicates an important ongoing event.

A change in camera angle, lens, lighting, shot size, or descriptive wording alone does not establish a new beat.

## Chronological state progression

Maintain a persistent state ledger for every scene.

Before planning a beat, inspect the preceding beat's resulting state.

The new beat must begin from that state and describe a physically plausible next event.

Never reset a character, object, location, or interaction to its original condition unless an explicit action causes that reset.

Examples:

- A closed door cannot become open without an opening action.
- A phone cannot transfer from Mother to Student without a handoff.
- A phone cannot display a new caller ID without a screen transition.
- A character cannot react to a revelation before that revelation occurs.
- An object cannot appear in two characters' hands simultaneously unless the physical interaction supports it.

## Physical action representation

Every beat must specify:

- The primary subject.
- The observable physical action.
- The action's starting state.
- The resulting state.
- The narrative purpose of the visual moment.

Prefer specific physical verbs over vague descriptions.

Examples of specific actions:

- reaches, grips, turns, pushes, opens, extends, transfers, receives, presses, lifts, recoils, freezes, looks, lowers.

Avoid generic descriptions that do not establish a physical event:

- the atmosphere changes
- the environment feels different
- the camera emphasizes the subject
- the scene becomes more intense

Atmospheric changes may supplement a physical event but cannot replace it.

## Beat uniqueness

Compare each proposed beat against all preceding beats in its scene.

If the subject, physical action, object state, narrative purpose, and visual information are substantially unchanged, do not generate another independent beat.

Instead:

- Extend the existing beat's duration if the action is continuous.
- Merge the narration fragments into one beat if they describe the same event.
- Create a new beat only when a new physical moment, meaningful state change, or necessary reaction occurs.

A new camera perspective is permitted when it reveals meaningful information that was not previously visible.

## Narration alignment

Preserve the exact source narration and its chronological order.

Do not omit, rewrite, or invent spoken words.

Narration fragments are timing and alignment information, not mandatory visual beat boundaries.

Multiple narration fragments may belong to one visual beat.

One narration fragment may contain multiple visual beats when its duration and physical events justify the division.

Never invent physical actions solely to fill a requested number of beats.

## Visual prompt generation

Generate prompts only after the physical action sequence has been established.

Each prompt must describe the actual moment assigned to that beat.

Include the relevant character identity, physical action, object state, composition, camera perspective, and visual style.

Character and location continuity must be preserved.

Do not add generic prefixes or camera terminology to disguise a repeated visual description.

Do not duplicate the complete scene premise in every beat.

## Final validation

Before returning the storyboard:

1. Verify chronological physical continuity.
2. Verify that every beat has a meaningful visual purpose.
3. Detect repeated physical events and unchanged states.
4. Merge unnecessary micro-beats.
5. Confirm that all source narration is preserved.
6. Reject empty or incomplete visual prompts.
7. Return only the validated storyboard in the requested schema.

If the narration does not support enough distinct physical events, return fewer beats rather than inventing repetitive action.

This instruction is intentionally strict about physical progression but allows sustained shots. That distinction matters: not every beat needs a new action, but every new beat must have a reason to exist.

## 3. Physical state tracking schema

The state ledger should be independent of the generated image prompt.

Do not attempt to recover physical continuity by comparing the final prompt text. The prompt is a description of the state, not the authoritative source of truth.

### Suggested TypeScript schema

```

type CharacterId = string;
type ObjectId = string;
type StateValue = string | number | boolean | null;

interface PhysicalState {
  characterStates: Record<CharacterId, {
    position: string;
    orientation: string;
    pose: string;
    gaze: string;
    expression: string;
    heldObjects: ObjectId[];
  }>;

  objectStates: Record<ObjectId, {
    location: string;
    holder: CharacterId | null;
    condition: string;
    attributes: Record<string, StateValue>;
  }>;

  environmentStates: Record<string, StateValue>;
}

interface StateTransition {
  entityId: string;
  property: string;
  from: StateValue;
  to: StateValue;
  cause: string;
}

interface KinematicBeat {
  beatId: string;
  sceneId: string;

  narration: string[];
  durationSeconds: number;

  action: {
    subject: string;
    verb: string;
    target?: string;
    startingState: string;
    endingState: string;
    causalReason: string;
  };

  stateBefore: PhysicalState;
  stateAfter: PhysicalState;

  transitions: StateTransition[];

  visualPurpose: string;
  camera: {
    shotSize: string;
    angle: string;
    movement: string;
    composition: string;
  };

  visualPrompt: string;
  previousBeatId?: string;
  validation: {
    stateContinuity: boolean;
    actionProgression: boolean;
    visualNovelty: boolean;
    narrationCoverage: boolean;
  };
}

```

The schema separates three concepts:

- Physical state: What is true at this moment?
- State transition: What changed and why?
- Visual prompt: How should the moment be represented visually?

The planner should generate the first two before generating the third.

### Example: door and phone state machines

```

type DoorState =
  | "closed"
  | "hand_on_knob"
  | "cracked_open"
  | "swung_wide";

type PhoneState =
  | "held_by_mother"
  | "extended_toward_student"
  | "transferring"
  | "held_by_student";

type ScreenState =
  | "off"
  | "backlit"
  | "incoming_call"
  | "caller_id_revealed"
  | "static"
  | "unanswered_call";

```

For the actual StoryFrame implementation, I recommend storing the states as strings with explicit transition rules, rather than relying exclusively on TypeScript union types. The unions are useful for known state machines, but a production application may need to support arbitrary user-created objects and events.

The state ledger should also support multiple objects of the same type. Mother and Student have separate phones, and the storyboard contains a coffin phone as well. Treating every phone as one global object would create continuity errors.

## 4. Intelligent beat aggregation vs. micro-splitting

The narration should determine what the viewer hears, while the physical action sequence determines what the viewer sees.

A phrase does not deserve a new visual prompt simply because the speech-to-text or timing system split it into a new chunk.

### Recommended decision rules

| Situation                                                   | Decision                                                 |
| ----------------------------------------------------------- | -------------------------------------------------------- |
| Multiple narration fragments describe one continuous action | Merge into one visual beat                               |
| Same action continues with no meaningful state change       | Sustain the shot                                         |
| A new action changes the physical state                     | Create a new beat                                        |
| A reaction follows a revelation                             | Create a new beat if the reaction is visually meaningful |
| A new camera angle reveals new information                  | Create a new beat if the revelation matters              |
| A short narration fragment contains no new visual event     | Attach it to an existing beat                            |
| A narration fragment has no possible visual representation  | Preserve the narration without inventing a visual event  |

The correct output may therefore contain fewer beats than the number of narration chunks.

For example, the line “Pinakita niya sa akin ang phone niya na ring nang ring” does not require four independent images. It describes one presentation of a phone and an ongoing ringing event.

A more useful visual sequence would be:

1. Mother extends the phone.
2. Student receives it.
3. The phone lights up with an incoming call.
4. The student reacts to the caller information.

The narration can remain attached to the appropriate beats without being rewritten.

### Duration-aware aggregation

Use duration as a constraint, not as the primary beat-generation rule.

A 3-second phrase may support one continuous visual event, while a single short sentence may contain several distinct actions.

For text-to-image mode, a sustained shot can be represented by one still image with a longer display duration. For text-to-video mode, the same shot may contain a continuous action with multiple observable phases.

The important distinction is that a beat is a visual event, not a fixed number of words or seconds.

## 5. True algorithmic deduplication and re-prompting

Your current deduplicator is operating at the wrong level.

Adding camera language to an identical description does not produce a distinct visual moment. It only changes the wording.

The solution is to compare the physical action and state transitions before comparing the final prompt text.

### Recommended validation pipeline

```

interface BeatValidationResult {
  duplicate: boolean;
  reason: string;
}

function validateBeatProgression(
  previous: KinematicBeat,
  current: KinematicBeat
): BeatValidationResult {

  const previousAction = previous.action;
  const currentAction = current.action;

  const sameAction =
    previousAction.subject === currentAction.subject &&
    previousAction.verb === currentAction.verb &&
    previousAction.target === currentAction.target;

  const sameState =
    JSON.stringify(previous.stateAfter) ===
    JSON.stringify(current.stateAfter);

  const samePurpose =
    previous.visualPurpose === current.visualPurpose;

  const hasStateTransition =
    current.transitions.length > 0;

  const hasNewVisualPurpose =
    current.visualPurpose !== previous.visualPurpose;

  const sameCamera =
    previous.camera.shotSize === current.camera.shotSize &&
    previous.camera.angle === current.camera.angle &&
    previous.camera.movement === current.camera.movement;

  if (
    sameAction &&
    sameState &&
    samePurpose &&
    !hasStateTransition &&
    !hasNewVisualPurpose
  ) {
    return {
      duplicate: true,
      reason: "No meaningful physical or narrative progression."
    };
  }

  if (
    sameState &&
    samePurpose &&
    !hasStateTransition &&
    sameCamera
  ) {
    return {
      duplicate: true,
      reason: "Repeated visual information without a new event."
    };
  }

  return {
    duplicate: false,
    reason: "Distinct physical or narrative moment."
  };
}

```

This is a baseline validation function. It is not a complete semantic deduplicator, but it demonstrates the correct validation target.

For a production implementation, I would use three independent checks:

1. Exact and normalized text similarity to catch obvious copies.
2. Semantic similarity between the action, state transitions, and visual purpose.
3. Chronological state validation to reject impossible or redundant events.

The first check is inexpensive and deterministic. The second catches paraphrased duplicates. The third catches physical continuity errors even when the descriptions are completely different.

### Semantic duplication scoring

Use an LLM or embedding model to compare structured beat representations, not only the raw prompts.

The comparison should answer:

- Is this the same physical event?
- Does the new beat reveal new information?
- Does an object or character change state?
- Is the new shot necessary to understand the story?
- Could both beats be represented by one continuous shot?

A duplicate score should be based on these semantic properties, rather than a single similarity threshold on the final prompt text.

A prompt can have low textual similarity and still depict the same event. Conversely, two similar prompts may represent different moments if the physical state has changed.

### Repair strategy

When a beat fails validation:

1. Re-plan the action from the previous beat's resulting state.
2. If no new event is supported by the narration, merge it with the previous beat.
3. If a new event is supported, generate a new action and state transition.
4. Regenerate the visual prompt from the repaired action.
5. Revalidate the repaired sequence.

Do not automatically append a different camera angle or descriptive phrase.

Also, do not retry indefinitely. If the model cannot produce a valid new event after a limited number of attempts, merge the beat or return a validation failure.

The following examples are particularly important because they teach the model what counts as a genuine visual change.


The narration can be continuous across these beats. The visual sequence advances because the physical event advances.

### Example B — Incorrect and correct phone progression

Incorrect:

- Mother holds the ringing phone.
- Mother holds the ringing phone from another angle.
- Mother holds the ringing phone in a closer shot.

Correct:

- Mother extends the phone toward the student.
- Student reaches out to receive it.
- The phone changes hands.
- The screen lights up with an incoming call.
- The student sees the caller information.

The correct sequence introduces physical transitions and new information, not merely new camera perspectives.

### Example C — Sustaining an ongoing shot

Suppose the narration says:

“Ramdam ko na parang may nasa kabila nga.”

The shot can sustain the student's phone and the dark hallway while the narration continues.

A new beat becomes justified when the disturbance changes:

- The screen begins to distort.
- The student notices the disturbance.
- The hallway light flickers in response.
- The unseen presence becomes physically perceptible.

These are separate visual events. Repeating the same vague silhouette four times is not.

## 7. Step-by-step implementation roadmap

### Phase 1 — Introduce structured planning

Replace direct narration-to-prompt generation with narration-to-action-plan generation.

The action planner should return the physical event sequence, the state ledger, and the visual purpose of each beat.

Keep the current continuity sheets, but move their role from prompt text into structured reference data.

### Phase 2 — Add beat aggregation

Group narration fragments before generating image prompts.

The aggregation stage should identify which fragments belong to the same physical event and which ones represent new events.

This stage should be allowed to reduce the number of beats.

### Phase 3 — Generate prompts from state transitions

Generate the image prompt from:

- The starting state.
- The physical action.
- The resulting state.
- The visual purpose.
- The camera and composition.
- The relevant character and location continuity.

The prompt should describe only the necessary physical details for the current moment.

### Phase 4 — Add validation and repair

Run the state continuity and semantic duplication checks before exporting the storyboard.

Repair invalid beats by re-planning or merging them.

Never disguise a duplicate by adding generic camera terminology.

### Phase 5 — Add production tests

Create regression tests using the exact scenes in the attached export.

At minimum, test:

- Door opening and mother reveal.
- Phone handoff and incoming call.
- Caller ID revelation.
- Unanswered call.
- Unseen presence escalation.

The tests should verify the sequence of state transitions, not merely the presence of different words in the generated prompts.

## 8. Final architectural recommendation

The strongest design for StoryFrame is a state-driven cinematic planner with a separate prompt compiler and a deterministic validation layer.

The LLM should be responsible for interpreting the story and proposing plausible physical events. The application should be responsible for enforcing chronological continuity, validating state transitions, and rejecting redundant beats.

That separation is what makes the system reliable.

A well-written prompt alone will not permanently eliminate duplication. The system needs an explicit representation of what has already happened, what changes next, and why the next visual moment deserves to exist.

For StoryFrame, I would prioritize the state ledger and beat aggregation before attempting more sophisticated semantic deduplication. Once the model is generating structured physical events, the deduplication problem becomes much easier to solve and the resulting storyboard will be more coherent, more cinematic, and more useful for both text-to-image and text-to-video production.
